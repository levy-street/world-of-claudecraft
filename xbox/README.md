# Xbox console shell

A UWP host that runs the game on an Xbox with a controller. It is the console
sibling of `electron/` (desktop) and `android/` + `ios/` (Capacitor): a thin
native shell around the same web client, which ships **unmodified**.

```
xbox/
  WorldOfClaudecraft.Shell.sln
  WorldOfClaudecraft.Shell/
    App.xaml(.cs)          host application, view setup
    MainPage.xaml(.cs)     the WebView2, navigation guards, crash recovery
    GamepadBridge.cs       Windows.Gaming.Input -> web message channel
    Assets/
      gamepad-polyfill.js      republishes the pad as navigator.getGamepads()
      console-memory-guard.js  console graphics budget, applied pre-boot
      *.png                    tiles, generated by build_tiles.py
    Properties/Default.rd.xml  .NET Native runtime directives
    web/                       the built client, staged at package time
  build_tiles.py
```

## Why a WebView2 UWP app and not a hosted web app

The obvious packaging route is a hosted web app: an MSIX whose `Application`
element points `StartPage` at the live site. On Xbox that runs on the legacy
EdgeHTML engine, and EdgeHTML has no WebGL2. three.js dropped WebGL1 in r163,
so such a package installs, launches, and renders nothing. A WinUI 2 UWP app
hosting a `WebView2` control gets the Chromium engine instead.

The client is packaged **inside** the MSIX and served from the virtual host
`https://app.local`, rather than loaded from the site. That gives an instant
boot, a session that works with no network at all (offline play and local
character saves), and no dependency on any server staying up. Online play still
works when there is a connection: the client's own net layer reaches the API,
whose CORS allow-list carries `https://app.local` (`XBOX_APP_ORIGIN` in
`server/web_login_guard.ts`).

That origin is its own client class on the server, not a member of
`NATIVE_APP_ORIGINS`. The native set means "proves itself with a platform
attestation"; UWP has no equivalent of the Capacitor attestation bridge, so
folding the console in there would fail console sign-in closed wherever
attestation is required, and would hand an Origin-only client the Seeker
entitlement and daily-reward branches. The console is admitted by Origin for
the bot gate exactly like the Electron desktop shell, and for the same reason:
a Turnstile widget cannot pass Cloudflare's domain validation at a private
virtual host, so there is no token it could send.

## Controller input

The Gamepad API does not reach WebView2 content on UWP
([WebView2Feedback#4366](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4366),
open since Feb 2024, no documented workaround). So `GamepadBridge` reads
`Windows.Gaming.Input` natively at compositor rate and posts standard-mapping
pad state over the WebView message channel; `Assets/gamepad-polyfill.js` is
injected at document-create and republishes it through `navigator.getGamepads()`
before any page script runs. `src/game/gamepad_map.ts` and the remap UI work
unchanged, and nothing console-specific enters the client.

Three keys are claimed by the host before the page sees them:

- **B**, because unclaimed it is the console back gesture and tears the app
  down mid-combat. Claiming the KEY does not hide the BUTTON, which still
  reaches the page through the bridge.
- **View** and **Menu**, because WebView2 on Xbox offers to switch out of
  gamepad mode into a mouse cursor when they are pressed, and this app has no
  cursor UI to switch back with.

Since B cannot be the way out, **hold View + Menu together for 1.5 seconds** to
exit.

## Crash recovery, and why the input path is separate from the exit path

Consoles kill the WebView2 render process far more readily than desktops, on a
tight per-app memory budget. Handling `ProcessFailed` by simply stopping is a
dead end that looks like this on a TV: a permanent banner over a half-alive
world, the character running into a wall forever, and no button doing anything,
exit included.

Two things cause that, and both are fixed here:

1. Stopping the bridge also killed the native read loop that carries the exit
   combo. `GamepadBridge.Stop()` now pauses only the *posting* side; the
   `CompositionTarget.Rendering` loop and the exit combo survive any web-side
   failure.
2. The page's polyfill was left frozen at the last-held stick, and the game
   re-applies that state every frame. Pausing now posts
   `{"t":"pad","connected":false}` first, so the polyfill releases every button
   and axis.

`ProcessFailed` is then handled by kind: render and GPU deaths reload the
packaged client in place, bounded at three recoveries per five minutes, and
only `BrowserProcessExited` or a crash loop shows a terminal message.

`Assets/console-memory-guard.js` attacks the same crashes at the source. It
pins `devicePixelRatio` to 1 (a fourfold cut in every backing buffer on a 4K
panel, invisible at couch distance) and floors the persisted graphics settings
to a console ceiling before the tier resolves. Keys and ranges come from
`src/game/settings.ts`; the client is not modified.

## The one line that killed every launch

Worth recording, because the crash dump points somewhere else entirely. The
June 2026 Xbox System OS (10.0.26100) fails the
`Application.RequiresPointerMode` setter with `E_NOTSUPPORTED`, which .NET
Native rethrows as `NotSupportedException` through the interop stub, unhandled,
two lines into `OnLaunched`. Every launch died behind the splash, and the dump
showed only a stowed `0x80131515` in combase/XAML frames, which mimics the
classic missing-`rd.xml` failure.

The console OS retires these legacy view APIs over time, so every cosmetic view
tweak in `App.xaml.cs` (layout scaling, pointer mode, desired bounds, the
`SystemNavigationManager` back-claim) is guarded individually. Losing one is
cosmetic; dying at the splash is not.

`Properties/Default.rd.xml` is real too, and must be registered as
`<Content Include="..." />`. Both `<None>` and `<RdXmlFile>` are silently
ignored, and building without directives is only warning ILT0027, so the
workflow greps the build log for it rather than trusting the file.

## Tests

Everything from the WebView message onward is plain JS, so both injected scripts
are covered by ordinary vitest files with the host channel stubbed:

- `tests/xbox_gamepad_polyfill.test.ts` feeds the exact payloads
  `GamepadBridge.Serialize()` emits and asserts the standard mapping, the
  inverted Y axis, that B reaches the page, that a disconnect mid press releases
  every button and axis, that reconnect re-announces, and that the file is inert
  outside the shell.
- `tests/xbox_console_memory_guard.test.ts` asserts the DPR pin, the first-run
  seed, that the clamp only ever moves settings down, and that a corrupt blob
  cannot throw before the game boots.

Only the two native hops (`Windows.Gaming.Input` into `GamepadBridge`, and
`PostWebMessageAsJson`) sit outside those tests.

## Building

CI: run the **Xbox MSIX** workflow (`.github/workflows/xbox-msix.yml`) from the
Actions tab. It is manual-dispatch only and costs nothing until asked. It
builds the client, stages it into `WorldOfClaudecraft.Shell/web`, and uploads
both a sideload `.msix` and a Store `.msixupload`.

Locally, with the Visual Studio "Universal Windows Platform development"
workload installed:

```sh
pnpm install --frozen-lockfile
pnpm run build:native
mkdir -p xbox/WorldOfClaudecraft.Shell/web && cp -r dist/* xbox/WorldOfClaudecraft.Shell/web/

msbuild xbox/WorldOfClaudecraft.Shell.sln /t:Restore /p:Configuration=Release /p:Platform=x64
msbuild xbox/WorldOfClaudecraft.Shell/WorldOfClaudecraft.Shell.csproj \
  /p:Configuration=Release /p:Platform=x64 /p:AppxBundle=Never \
  /p:UapAppxPackageBuildMode=StoreAndSideload /p:AppxPackageSigningEnabled=false
```

Use `StoreAndSideload`, not `StoreUpload`. `StoreUpload` emits only the
`.msixupload`, whose sideload sibling references its framework packages without
shipping them; that deploys to a console cleanly and then dies right after the
splash, because managed code cannot start without `Microsoft.NET.Native.Runtime`
and there is no XAML without `Microsoft.UI.Xaml`.

Tiles are regenerated from `public/icon-512.png` with `python xbox/build_tiles.py`
(needs Pillow).

## Sideloading to a dev console

The package identity in `Package.appxmanifest` is a placeholder. Anyone
publishing to the Store replaces `Name` and `Publisher` with their own Partner
Center values and signs with the matching certificate.

For a dev kit, sign with any self-signed certificate whose subject equals the
manifest `Publisher`, then install through the Xbox Device Portal
(`https://<console-ip>:11443`). Unsigned packages are rejected with
`0x800B0100`. The portal's write endpoints need the `CSRF-Token` cookie from a
`GET /` echoed back as an `X-CSRF-Token` header, and a dev kit refuses to launch
any sideloaded app until an Xbox profile is signed in.

For profiling, drop an empty file named `woc-devtools` into the app's
`LocalState` folder: Release builds then enable
`msEdgeDevToolsWdpRemoteDebugging`, so Chrome DevTools can attach over the
Device Portal (the Xbox Edge browser has none). A Store package never has that
file. Note that the Device Portal goes unresponsive while a GPU-heavy page
runs, so attach on a menu rather than mid-gameplay.

## Known gaps

- Sign-in with Discord or SSO cannot work in this shell (popup plus wrong-origin
  token); password sign-in does. The fix is a login-code flow (issue #2816).
- Console controller edge cases are tracked in issue #2813.
- The shell's own status strings live in C# and are English only. The desktop
  shell solves the same problem by having the renderer push `t()`-rendered
  strings to the main process (`electron/shell_strings.cjs`); the same approach
  fits here and is not implemented yet.
